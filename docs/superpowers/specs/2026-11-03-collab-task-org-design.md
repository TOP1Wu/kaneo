# 协作任务 + 组织架构 + 负责人看板 + 仪表盘 设计文档

- 日期：2026-11-03　状态：待华少批准
- 仓库：TOP1Wu/kaneo，分支 dev（基于上游 v2.48.0，自有改动 0）
- 需求来源：企业微信智能表「AI创新产品规划需求池」（34 人，15 条需求，4 条产品线）
- 仓库规范：严格遵守根目录 `AGENTS.md`（迁移、Zod/OpenAPI、publishEvent、i18n、权限在 API 侧校验）

## 1. 要解决的问题

现在一个需求只能挂一个负责人（`task.assignee_id`），产品、开发、测试只能各建一张单，没法协作完成同一个任务；
管理者看不到下属在所有产品线上的进度，也不知道卡在哪里；没有仪表盘。

## 2. 硬约束

1. **主表 `task` 不加列、不改列**。所有新能力走扩展表，降低合并上游的冲突。
2. 现有依赖 `assignee_id` 的逻辑（约 53 个 API 文件：GitHub/GitLab/Gitea 同步、通知、导入导出、搜索）保持可用。
3. 单实例不依赖 Redis 也能跑（上游原则）。
4. 权限一律在 API 侧校验，隐藏按钮不算权限。

## 3. 功能清单

| # | 功能 | 一句话 |
|---|---|---|
| F1 | 任务成员（多角色、多人） | 一张任务挂多个人，每人带角色；角色可配置，默认 主要负责人 / 产品 / 开发 / 测试，每种角色都可多人 |
| F2 | 个人完成标记（并行） | 每人一条进度：未开始 / 进行中 / 已完成；互不阻塞；全员完成后亮「可验收」，主要负责人手动关单 |
| F3 | 我的任务 | 只要我是成员，任务就进我的「我的任务」，显示我的角色和我的进度 |
| F4 | 流程变更日志 | 加人、移除、换角色、改进度、撤回、代改，全部记谁、何时、前后值 |
| F5 | 组织架构 | 管理员维护部门树和每个部门的领导；上级可看下级（含下下级）所有任务与进度 |
| F6 | 负责人看板 | 跨全部产品线，按人分列，可切「我的下属 / 某部门 / 全部」 |
| F7 | 仪表盘 | 跨全部产品线的指标卡与图表，含「卡点」分析 |

## 4. 数据模型（全部新增表，`task` 不动）

### 4.1 `task_role` 角色字典（工作区级）
| 列 | 说明 |
|---|---|
| id, workspace_id | |
| name, slug, color, position | 默认种子：主要负责人(`owner`) / 产品(`product`) / 开发(`dev`) / 测试(`qa`) |
| is_owner_role | 布尔，仅一个角色为 true（默认「主要负责人」），用于同步 assignee 与验收权 |
| archived_at | 停用而非删除，保留历史日志可读 |

### 4.2 `task_member` 任务成员（一人一角色一行）
| 列 | 说明 |
|---|---|
| id, task_id(→task cascade), user_id(→user cascade), role_id(→task_role) | 唯一约束 (task_id, user_id, role_id)；同一人可同时担两个角色（两行） |
| progress | `todo` / `doing` / `done` |
| started_at, done_at, note | 进度时间点与个人备注 |
| position | 同角色内排序 |
| updated_at, updated_by | 最近一次谁改的（可能是代改） |

索引：`(user_id, progress)` 供「我的任务」/看板；`(task_id)`。

**assignee 同步规则**：「主要负责人」角色下 position 最小的人写入 `task.assignee_id`；被移除时由下一位顶上；无人时置空。所有写 `task_member` 的入口统一走一个 `syncPrimaryAssignee(taskId)`。反向：老入口（MCP `update_task_assignee`、GitHub 同步）改了 assignee 时，自动把该人补进「主要负责人」第一位。

### 4.3 组织架构
- `org_unit`：id, workspace_id, parent_id(自引用，可空=根), name, position。部门树，层级不限。
- `org_unit_member`：org_unit_id, user_id, is_leader(布尔)。一人可在多个部门；一个部门可有多个领导。

**谁是我的下级**：我担任 leader 的部门及其所有子孙部门里的全部成员（不含我自己）。用 Postgres 递归 CTE 计算，不做缓存表。

### 4.4 日志：复用 `activity` 表（不改结构）
新增 `type`：`member_added` / `member_removed` / `member_role_changed` / `member_progress_changed` / `task_ready_for_review`。
`event_data` 存 `{ memberUserId, roleId, roleName, from, to, onBehalfOf? }`。`userId` 是操作人；代改时 `onBehalfOf` = 被改的人，时间线渲染为「何欣 代 胡楠（开发）标记完成」。
同时 `publishEvent()` 推实时与 webhook（事件名 `task.member_*`），供以后 agent 回写使用。

## 5. 权限

| 视角 | 谁 | 能看 | 能改 |
|---|---|---|---|
| 超级管理员 | 实例 `admin` | 全实例所有工作区的组织架构、看板、仪表盘 | 一切 |
| 管理员 | 工作区 `owner` / `admin` | 本工作区全部人员与任务 | 维护组织架构、角色字典 |
| 上级领导 | `org_unit_member.is_leader` | 自己 + 全部下级（递归）的任务与进度，**跨全部产品线** | 下级的进度可代改（记日志） |
| 主要负责人 | 该任务「主要负责人」角色 | 该任务全部成员进度 | 增删成员、代改进度、关单 |
| 普通成员 | 任务成员 | 自己参与的任务 | 只改自己那一行进度 |

**跨项目可见性的口径（需注意）**：Kaneo 现有 `workspace_member_project` 会限制成员只能看部分项目。领导通过组织架构看到下级任务时，**按领导身份放行**（视为对下级参与的任务有只读权）。所有放行在 API 的 controller 内判断，不在前端。

## 6. 页面与交互

### 6.1 任务详情 → 「成员」区块
按角色分组列出成员（头像 + 名字 + 进度下拉 + 完成时间）；「+ 添加成员」选人 + 选角色（可多选人）。
自己那一行可改进度；主要负责人、上级、管理员可改别人（显示「代改」提示）。

### 6.2 任务卡片 / 列表
新增一列「成员进度」：`产品 2/2 · 开发 1/3 · 测试 0/2`，全员完成时显示「可验收」徽标。列表可按 角色、成员、个人进度 筛选/分组。

### 6.3 我的任务
数据源改为：`assignee_id = 我` **或** `task_member.user_id = 我`（去重）。每条显示「我的角色 + 我的进度」，可直接在列表里改自己的进度。分组新增「按我的进度」。

### 6.4 组织架构（设置 → 组织架构，管理员可见）
左侧部门树（拖拽调层级），右侧成员列表，勾选「领导」。

### 6.5 负责人看板（新页面，工作区级，跨全部产品线）
- 范围切换：**我的下属**（默认，领导）/ 某部门 / 全部（管理员）
- 每列一个人，列头：姓名、部门、进行中数、逾期数、**卡点数**
- 卡片：产品线、标题、他的角色、他的进度、截止日、优先级
- 筛选：产品线、角色、个人进度、优先级、是否逾期

### 6.6 仪表盘（新页面，工作区级，跨全部产品线，按「范围」同 6.5）
- 指标卡：需求总数、各需求状态数、逾期数、可验收数、**卡点数**
- 任务分工：横轴人，按个人进度堆叠（按人去重，不会再出现 15 条算成 19）
- 产品线分布：每条产品线 × 需求状态
- 角色环节完成率：产品 / 开发 / 测试 各自 done 比例 → 看卡在哪个环节
- 卡点榜：列出被卡任务 + 卡在谁 + 卡了几天
- 筛选：产品线、时间段（按创建/截止）

### 6.7 「卡在哪里」的定义（我的口径，可改）
一条任务算「卡点」，满足任一：
1. 已过截止日，且有成员未完成 → 卡在**这些未完成的人**
2. 某成员处于 `doing` 超过 N 天无变化（N 默认 7，工作区可配）→ 卡在**此人**
3. 同任务其他角色都完成，只剩某一角色未完成 → 卡在**该角色**

卡在谁 = 该任务里未完成的成员；卡了几天 = 距其最近一次进度变化的天数。

## 7. 对外接口（API / MCP）
- REST：`/task-member`（增删改、改进度）、`/task-role`、`/org-unit`、`/leader-board`、`/dashboard`，全部 Zod + OpenAPI。
- MCP 新增：`list_task_members`、`add_task_member`、`remove_task_member`、`update_my_task_progress`。供以后本地 agent 完成后自动回写「开发 已完成」。
- `get_task` / `list_tasks` 的返回补充 `members` 摘要（新增字段，不破坏老字段）。

## 8. 迁移与数据
- 一个 Drizzle 迁移，只建新表；种子为每个已有工作区插入 4 个默认角色。
- 回填：现有每个 `assignee_id` 非空的任务，插入一行「主要负责人」成员，进度按任务所在列推断（终态列 → done，其余 → doing）。
- 回滚：删新表即可，`task` 无改动。

| 期 | 内容 | 验收 |
|---|---|---|
| P1 | F1 成员表 + F2 进度 + F4 日志 + 任务详情/卡片 UI + assignee 同步 | 一张单挂 产品2/开发3/测试2，各自勾选，日志完整，GitHub 同步不坏 |
| P2 | F3 我的任务 + MCP 新工具 | 七个人登录都能在「我的任务」看到同一张单 |

| P4 | F6 负责人看板 + F7 仪表盘 + 卡点 | 用需求池 15 条数据导入后，看板与仪表盘数字和 Excel 对得上（去重后） |

每期都要：`pnpm` 类型检查 + 单测 + `tests/api` 通过；前端给华少可点开的预览地址。

## 10. 不做（本期）
词云；需求收集表单（字段只有 2 个，后续再说）；自定义自动化规则；移动端 App 适配（`apps/mobile` 只保证不崩）。

## 11. 我替你做的决定（可推翻）
1. 全员完成 → 亮「可验收」，主要负责人手动关单，不自动挪列。
2. 本人 + 主要负责人 + 上级 + 管理员可改进度；非本人修改一律记「代改」。
3. 一人可同时担两个角色。
4. 上级可见范围递归到所有子孙部门。
5. 卡点阈值 N = 7 天，工作区可配。
6. 主要负责人第一位同步到 `task.assignee_id`，保证老功能不坏。
